<assumption_delta_decision>
**Noun now primary:** the *generalized CICS command* — statement identity is carried by one node
with `field('command', ...)` rather than by a verb-class-specific rule name.

**Delta type:** pluralization. Phase 2's D-01 modelled statement identity per verb class
(`idms_navigation_statement`, `idms_session_statement`, `idms_update_statement`,
`idms_accept_statement`). D-17 generalizes CICS to a single `exec_cics_statement`.

**Decision: `add-alongside`.** D-17 is locked, so the IDMS four-verb-class shape is NOT promoted
to the generic shape and NOT retired; the two shapes coexist in `grammar.js`. Rationale: IDMS DML
is positional, so its verbs genuinely cluster into distinct operand shapes; CICS is uniformly
`COMMAND KEYWORD(arg) ...`, so verb classes buy nothing and would leave unmeasured commands
homeless.

**Accepted debt:** the grammar now carries two statement-identity conventions, and
`queries/idms.scm` and `queries/cics.scm` read differently for the same conceptual role
(verb-class node name vs. `command:` field). A consumer building edges across both families must
know which convention applies to which family.

**Forcing function for a later promote:** Phase 4's `EXEC SQL`. If `EXEC SQL` also lands as a
generic `field('command', ...)` node, two of three families use the generic shape and IDMS is the
outlier — at which point promoting IDMS to a generic `idms_statement` with `field('verb', ...)`
becomes the smaller change. OQ-1 is still open on exactly this axis.

**Suggested (not required) invariant test:** a corpus case asserting that every
`exec_cics_statement` exposes a `command:` field regardless of which command word appears, so the
generalized intent is encoded rather than implied by the rule name.
</assumption_delta_decision>
